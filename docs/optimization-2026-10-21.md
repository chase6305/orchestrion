# 工作流可靠性与资源作用域优化

本轮补齐单设备域的持久操作记录、保守重启核对、连续资源作用域和票据式设备协议。现有 TaskPilot 示例与回归测试继续通过；新增 API 位于实验性的 `orchestrion.workflow`，核心运行依赖仍为标准库。

## 执行与恢复行为

- `SQLiteJournal` 先提交运行与幂等键，再在实际设备调用之前提交操作意图。执行预算在同步落盘之后再次核对，慢提交不能放行已经过期的新命令。
- 完成的带键结果跨重启返回同一个运行 ID；进程中断的已派发操作恢复为 `UNKNOWN` 并占有原资源，未派发节点取消。恢复不自动重放设备命令，也不继续执行剩余 DAG。
- `context.checkpoint()` 保存票据等必要元数据，按紧凑 ASCII JSON 限制为 64 KiB；迟到票据可以在适配器退出前补记，历史 UNKNOWN 保持不变。核对证据单独保存在节点行，有限审计事件淘汰后仍然可读。
- 日志持有规范路径的生命周期锁，拒绝重复所有者及 fork 后沿用连接。缺失节点、资源缺失或累计容量不足会拒绝恢复。日志故障关闭派发入口，并请求合作停止。
- `workflow_action()` 将固定子 DAG 注册为一个能力，在进入之前原子取得列出资源的完整容量。内部支持依赖、输出绑定和容量并发；整段结束前保持外部资源占有。任一内部操作未知时，隔离整段资源。
- `TicketAction` 对接异步 submit/query/cancel 后端，区分命令受理、最终完成与停止确认。提交响应丢失不自动重发执行命令；连续查询失败和停止确认超期均保留未知。
- `Node.stop_timeout` 和引擎默认值提供独立停止确认预算。超期的适配器继续受追踪、保留并发槽位，退出后才能核对释放。关闭超时共享一次预算，可以随后继续等待。
- 输入、输出、反馈可分别设置单条字节额度；引用模板及解析后的输入都检查，超大结果不会进入保留历史或后继动作。
- `Action.version` 参与执行快照；组合能力自动对内部计划、版本与限额形成摘要。每个操作 ID 的节点组件单独编码，`run.operation_id(node_id)` 避免层级别名。

运行句柄与快照移至 `run.py`，恢复装配与容量核对移至 `recovery.py`；调度器继续负责执行与资源状态转换。嵌套执行上下文保留祖先等待检查，通过弱引用避免后台子任务持续保留已完成引擎。

## 性能记录

同机 Python 3.10.0、SQLite 3.53.2，命令顺序执行，采用多次运行中位数。内存模式基线来自本地提交 `d16a6d7` 的隔离源码副本；这里是无设备动作的调度微基准。

5000 节点、7 次运行，总耗时（毫秒）：

| 拓扑 | HEAD | 当前内存模式 | 变化 |
| --- | ---: | ---: | ---: |
| chain | 232.84 | 237.78 | +2.1% |
| wide | 183.35 | 209.58 | +14.3% |
| contended | 229.39 | 241.35 | +5.2% |

内存路径增加版本/检查点字段和执行上下文检查，本机采样显示约 2%–14% 的调度开销；本轮没有宣称内存调度吞吐提升。真实设备 I/O、线程和网络耗时不在这些数值中，单机样本也不构成性能保证。

50 节点、3 次运行，总耗时（秒）：

| 拓扑 | auto：WAL/FULL | 强制 rollback/EXTRA | 耗时比 |
| --- | ---: | ---: | ---: |
| chain | 0.533 | 2.319 | 4.35× |
| wide | 0.541 | 2.431 | 4.50× |
| contended | 0.532 | 2.404 | 4.51× |

WAL/FULL 在本机的同步工作流微基准中约为回滚模式的 4 倍速度，仍逐次提交操作意图和结果。SQLite 3.50.4 环境自动使用 rollback/EXTRA。模式依据 [SQLite WAL 文档](https://www.sqlite.org/wal.html) 与 [同步设置说明](https://www.sqlite.org/pragma.html#pragma_synchronous)：自动模式只在包含 WAL-reset 修复的版本上启用 WAL；其余采用带目录同步的回滚模式。代码识别官方列出的 3.51.3 及以上，以及 3.44.6 / 3.50.7 的回补分支。

```bash
python -m examples.benchmark_workflow --counts 5000 --repeats 7
python -m examples.benchmark_workflow --journal --counts 50 --repeats 3
python -m examples.benchmark_workflow --journal --journal-mode delete --counts 50 --repeats 3
```

## 当前边界

实际机械臂、PLC、底盘 SDK 尚未接入本轮测试；设备停止证明、协议级幂等和控制器重启语义由后端落实。核对接口保存证据并释放资源，不自行验证字符串是否代表物理停止。

组合能力接受固定计划，内部并发限额与外层分别计算；跨作用域的总量通过共享资源容量表达。任意图上的可重入 reservation scope、世界状态服务、自动补偿和分布式 fencing 保留在架构路线图。

同步磁盘提交仍在事件循环中执行，会增加延迟；这里不提供实时停止。输入/输出/反馈限额约束单条 JSON，而非进程 RSS 或历史总字节数。SQLite 历史显式清理并保留未决操作，图像和点云继续通过外部 artifact 引用传递。WAL 侧文件属于活动数据库，在线备份需使用 SQLite backup API。


## 后续快速收尾

用户将继续优化的三小时窗口调整为快速处理并结束。本轮完成以下增量：

- 增加 `dispatch.py` 提交屏障，合并同轮并发节点的派发意图；整个批次提交成功后才进入设备，失败则没有任何批次内适配器被调用。取消和超时仍在提交之后再次核对；在等待提交时被中断的未进入适配器操作不记作未知。
- 整图取消和失败传播中的节点终态使用一个原子事务，避免逐个同步提交；中途写入失败回滚整个状态转换，重开继续保守恢复。
- `TicketAction` 响应查询等待期间的取消，退出查询协程后发送停止请求；查询清理时间纳入停止确认预算。所有辅助任务在适配器退出前回收。
- 恢复检查拒绝运行中节点缺失租约、未知节点无租约且无核对证明、核对记录不一致及运行终态不符。未带幂等键的不一致未知记录也会被加载核对；拒绝恢复不修改数据库。

| --- | ---: | ---: |
| chain | 0.5184 | 0.5186 |
| wide | 0.5196 | 0.2793 |

并发图在该微基准中耗时减少约 46%，串行和单资源争用图基本持平。这里没有将磁盘提交迁出事件循环，独立节点结果仍逐次同步提交，不提供实时停止保证。对比原始数据保存在 `/tmp/orchestrion-round2-benchmark.json`；没有新增依赖、提交代码或发布。
