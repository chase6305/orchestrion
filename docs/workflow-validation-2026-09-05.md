## 第二轮持续优化

新增 `Workflow(timeout=...)`，用单调时钟统一限制依赖等待、资源排队和动作执行。到期会停止派发，正在运行的设备继续持有资源直到确认结束。节点超时会立即触发 `FAIL_FAST`，不等清理结束才停止同伴。

本轮复现并修复了以下生命周期问题：

- 所有节点成功后、运行状态汇总前到来的取消，不再重写最终成功状态。
- 整体取消或整体超时为未启动节点统一记录原因，结果不再依赖节点遍历顺序。
- SDK 调用出队时检查取消信号，已取消的排队调用不会进入设备函数；已经开始的函数继续等待最终结果。
- 执行器确认排队调用取消时正常释放资源；执行协程中断、无法确认设备状态时保留未知资源，并继续收集迟到的执行器异常。
- 动作不能等待本引擎的未完成运行或关闭本引擎，防止依赖自身完成的等待环。
- 调度任务启动失败会回滚提交；动作任务启动失败、启动前被取消、异常退出均会正确处理资源与终态。
- SDK 异常的字符串格式化失败不会使运行挂起。
- SDK 线程反馈在事件循环中追加，输入先复制，迟到反馈丢弃；已完成的上下文不能重新等待或启动 SDK 动作。

## 第三轮持续优化

本轮补齐重复请求、长期运行结果保留和资源等待排查三个实际接入问题。

- `submit(workflow, idempotency_key=...)` 在派发前登记执行快照摘要。同键同计划返回原句柄，不重复动作、不重置预算；计划变化直接报错。比较区分 JSON 标量类型、输出引用和形似引用的普通 JSON。
- `get_run_by_key()` 查询保留的运行。`max_idempotency_keys` 默认 1024，到达上限时拒绝新键，已有键仍可重复提交；不自动淘汰去重记录。
- `prune_idempotency_keys(keep_last=...)` 显式清理旧键。活动运行、尚有任何未核对未知操作的运行不可清理；清理之后允许该键再次执行，原句柄仍有效。
- `run.explain(node_id)` 说明依赖、并发、资源容量、资源队首、停止确认或未知隔离原因，并关联资源占用者的操作 ID。
- `engine.scheduler_snapshot()` 返回活动节点统计、资源占用者与队首、幂等键容量及可清理数量；按需读取，不调用设备，不调整调度队列。
- 模拟产线使用显式周期键；CI 安装包检查覆盖去重、查询、诊断与清理。

## 第四轮持续优化

复现了调度协程被取消后运行句柄一直保持 `RUNNING` 的问题。现在监督调度协程的取消、异常及提前退出：关闭新提交，失败未进入适配器的节点，请求活动作收尾。完成通知独立于调度协程，等待和关闭可以继续完成；资源仍以实际停止确认作为释放条件，未知操作继续隔离。

补充检查了资源预约与执行协程启动之间的空隙，以及故障回调尚未执行时的派发窗口。已排队协程在进入适配器前重新检查调度状态；没有进入适配器的预约可以回收。eager task factory 创建新调度任务时，避免把上一次正常完成的调度任务误判为本次故障。关闭等待者被取消或等待超时，不会取消设备收尾。

SDK 反馈新增 `max_pending_feedback_per_action`，默认每动作 128 条。首次跨线程报告时才创建反馈队列；每动作至多排入一个消费通知，每批最多投递 32 条后让出事件循环。满队列丢弃最旧的待投递进度，发送 `feedback_overflow` 事件，并把总数写入最终 `NodeResult.feedback_dropped`。终态之前刷新剩余队列，结束后的迟到反馈丢弃。

诊断新增 `scheduler_error` 和节点反馈积压/丢弃计数。事件历史有容量限制，最终结果中的丢弃计数不会随历史淘汰消失。反馈容量按条数计算，关键业务结果应由最终输出或设备协议承载。

## 第五轮整体优化

本轮贯通规划器目录、DAG 编译、设备输出及下游输入的数据契约，并让旧版服务请求复用相同校验能力。

- `FieldSpec` 支持 `items`、`object_schema`、`min_items` 和 `max_items`，可声明姿态向量长度、数组元素类型及嵌套对象字段。错误包含 `objects[0].pose[1]` 等具体路径。
- 组装父字段、父 schema 和引擎注册阶段分别复制约束，防止调用方后续修改嵌套对象影响已注册契约。
- `Action.output_schema` 声明 JSON 对象结果，在适配器返回后、记录成功和派发后继前验证；目录同时暴露输入和输出契约。
- 无效结果让产生结果的节点失败并记录 `ActionOutputError`，依赖节点跳过；可用的原始 JSON 结果保留用于排查，设备动作不自动重试或撤销。
- `RequestSchema.validate_path()` 和编译器提前拒绝已知不可能的输出引用，包括封闭对象的未知字段、访问错误类型和超过声明数组上界的下标。可选字段、短数组和开放结构仍由运行时检查。
- 模拟产线的视觉、底盘、机械臂、夹具和语音声明输出契约；机械臂输入也验证嵌套检测结果。姿态长度异常阻止后续操作，过期及未来时间戳在机械臂动作前拒绝。
- 复用字段类型检查函数，避免每次校验字段时重复创建验证函数和字典。

## 第七轮：带引用输入的提交前校验（最新）

复现了一个计划预检缺口：只要节点包含 `OutputRef`，原编译器就跳过该节点的整个输入 schema。机械臂姿态来自视觉引用、固定速度为 100、声明上限为 1 时，预览仍成功，视觉动作先执行，随后机械臂节点才因速度无效失败。

现在预览和提交逐字段检查已知部分：必填字段、额外字段、固定值的类型和范围、嵌套对象、数组元素及长度、组合枚举中的固定成员。引用值留待绑定后再次完整校验；发现已知错误时，整个计划在设备派发前拒绝，并且不占用幂等键或活动运行配额。

- `RequestSchema.validate_template(content, is_deferred=...)` 提供与引用表示无关的模板检查。它不修改模板，也不返回可执行输入；运行时仍使用 `validate()`。
- 组合枚举按结构比较；待绑定值只在其位置作为未知值，其余字段必须与至少一个候选匹配。合法引用在编译时通过，绑定后的错误值仍阻止消费节点进入设备函数。
- 修复 Python 相等比较导致的嵌套布尔值混淆：`{"stopped": 1}` 不再匹配 `{"stopped": true}`。整数和等值浮点数仍按数值比较，JSON 数组中的列表/元组表示保持兼容。
- 对允许额外字段的 schema 跳过不需要的未知字段集合计算；封闭对象直接比较字典键视图，减少临时集合。
- 新增 29 项参数化回归，归入现有 `test_schema.py` 和 `test_workflow_contracts.py`。安装包的 CI 检查增加了含引用输入的错误拒绝与幂等键回收验证。
